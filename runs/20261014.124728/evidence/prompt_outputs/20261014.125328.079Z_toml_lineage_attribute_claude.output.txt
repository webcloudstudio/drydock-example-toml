<requirement name="case-sensitive" stories="parser-lexical-boundaries">
TOML is case-sensitive.
</requirement>
<requirement name="utf8-document" stories="parser-lexical-boundaries">
A TOML file must be a valid UTF-8 encoded Unicode document.
</requirement>
<requirement name="whitespace-and-newline" stories="parser-lexical-boundaries">
Whitespace means tab (0x09) or space (0x20).
Newline means LF (0x0A) or CRLF (0x0D 0x0A).
</requirement>
<requirement name="comment-marker" stories="parser-lexical-boundaries">
A hash symbol marks the rest of the line as a comment, except when inside a string.
</requirement>
<requirement name="comment-control-characters" stories="parser-lexical-boundaries">
Control characters other than tab (U+0000 to U+0008, U+000A to U+001F, U+007F)
are not permitted in comments.
</requirement>
<requirement name="key-value-pair" stories="parser-keys,parser-strings,parser-arrays-inline">
Keys are on the left of the equals sign and values are on the right. Whitespace is ignored around key names and values. The key, equals sign, and value must be on the same line (though some values can be broken over multiple lines).
</requirement>
<requirement name="key-value-line-end" stories="parser-keys,parser-arrays-inline">
There must be a newline (or EOF) after a key/value pair.
</requirement>
<requirement name="values-typed" stories="parser-strings,parser-lexical-scalars,parser-datetimes,parser-arrays-inline">
Values must have one of the following types.
Unspecified values are invalid.
</requirement>
<requirement name="maps-to-hash-table" stories="parser-keys,parser-tables,parser-arrays-inline">
TOML is designed to map unambiguously to a hash table.
</requirement>
<requirement name="bare-keys" stories="parser-keys">
Bare keys may only contain ASCII letters, ASCII digits, underscores, and dashes (`A-Za-z0-9_-`).
</requirement>
<requirement name="bare-keys-digits-are-strings" stories="parser-keys">
Note that bare keys are allowed to be composed of only ASCII digits, e.g. `1234`, but are always interpreted as strings.
</requirement>
<requirement name="quoted-keys" stories="parser-keys">
Quoted keys follow the exact same rules as either basic strings or literal strings and allow you to use a much broader set of key names.
</requirement>
<requirement name="empty-keys" stories="parser-keys">
A bare key must be non-empty, but an empty quoted key is allowed (though discouraged).
</requirement>
<requirement name="dotted-keys" stories="parser-keys,parser-tables">
Dotted keys are a sequence of bare or quoted keys joined with a dot.
</requirement>
<requirement name="dotted-key-whitespace" stories="parser-keys">
Whitespace around dot-separated parts is ignored.
</requirement>
<requirement name="key-defined-once" stories="parser-keys">
Defining a key multiple times is invalid.
</requirement>
<requirement name="bare-and-quoted-keys-equivalent" stories="parser-keys">
Note that bare keys and quoted keys are equivalent:
</requirement>
<requirement name="dotted-key-extension" stories="parser-keys">
As long as a key hasn't been directly defined, you may still write to it and to names within it.
</requirement>
<requirement name="dotted-keys-out-of-order" stories="parser-keys">
Defining dotted keys out-of-order is discouraged.
</requirement>
<requirement name="dotted-keys-float-lookalike" stories="parser-keys">
Since bare keys can be composed of only ASCII integers, it is possible to write dotted keys that look like floats but are 2-part dotted keys.
</requirement>
<requirement name="indentation-ignored" stories="parser-keys,parser-tables">
Indentation is treated as whitespace and ignored.
</requirement>
<requirement name="string-basic" stories="parser-strings">
Basic strings are surrounded by quotation marks (`"`). Any Unicode character may be used except those that must be escaped: quotation mark, backslash, and the control characters other than tab (U+0000 to U+0008, U+000A to U+001F, U+007F).
</requirement>
<requirement name="string-compact-escapes" stories="parser-strings">
For convenience, some popular characters have a compact escape sequence.
</requirement>
<requirement name="string-unicode-escapes" stories="parser-strings">
Any Unicode character may be escaped with the `\uXXXX` or `\UXXXXXXXX` forms. The escape codes must be valid Unicode scalar values.
</requirement>
<requirement name="string-reserved-escapes" stories="parser-strings">
All other escape sequences not listed above are reserved; if they are used, TOML should produce an error.
</requirement>
<requirement name="string-multiline-basic" stories="parser-strings">
Multi-line basic strings are surrounded by three quotation marks on each side and allow newlines. A newline immediately following the opening delimiter will be trimmed. All other whitespace and newline characters remain intact.
</requirement>
<requirement name="string-newline-normalization" stories="parser-strings">
TOML parsers should feel free to normalize newline to whatever makes sense for their platform.
</requirement>
<requirement name="string-line-ending-backslash" stories="parser-strings">
When the last non-whitespace character on a line is an unescaped `\`, it will be trimmed along with all whitespace (including newlines) up to the next non-whitespace character or closing delimiter.
</requirement>
<requirement name="string-multiline-basic-quotes" stories="parser-strings">
You can write a quotation mark, or two adjacent quotation marks, anywhere inside a multi-line basic string.
</requirement>
<requirement name="string-multiline-basic-control-characters" stories="parser-strings">
Any Unicode character may be used except those that must be escaped: backslash and the control characters other than tab, line feed, and carriage return (U+0000 to U+0008, U+000B, U+000C, U+000E to U+001F, U+007F).
</requirement>
<requirement name="string-literal" stories="parser-strings">
Literal strings are surrounded by single quotes. Like basic strings, they must appear on a single line.
</requirement>
<requirement name="string-multiline-literal" stories="parser-strings">
Multi-line literal strings are surrounded by three single quotes on each side and allow newlines. Like literal strings, there is no escaping whatsoever. A newline immediately following the opening delimiter will be trimmed. All other content between the delimiters is interpreted as-is without modification.
</requirement>
<requirement name="string-multiline-literal-quote-limit" stories="parser-strings">
You can write 1 or 2 single quotes anywhere within a multi-line literal string, but sequences of three or more single quotes are not permitted.
</requirement>
<requirement name="string-literal-control-characters" stories="parser-strings">
Control characters other than tab are not permitted in a literal string.
</requirement>
<requirement name="integer-forms" stories="parser-lexical-scalars">
Integers are whole numbers. Positive numbers may be prefixed with a plus sign. Negative numbers are prefixed with a minus sign.
</requirement>
<requirement name="integer-underscores" stories="parser-lexical-scalars">
For large numbers, you may use underscores between digits to enhance readability. Each underscore must be surrounded by at least one digit on each side.
</requirement>
<requirement name="integer-leading-zeros" stories="parser-lexical-scalars">
Leading zeros are not allowed. Integer values `-0` and `+0` are valid and identical to an unprefixed zero.
</requirement>
<requirement name="integer-radix-prefixes" stories="parser-lexical-scalars">
Non-negative integer values may also be expressed in hexadecimal, octal, or binary. In these formats, leading `+` is not allowed and leading zeros are allowed (after the prefix).
</requirement>
<requirement name="integer-64-bit-range" stories="parser-lexical-scalars">
Arbitrary 64-bit signed integers (from −2^63 to 2^63−1) should be accepted and handled losslessly. If an integer cannot be represented losslessly, an error must be thrown.
</requirement>
<requirement name="float-ieee-binary64" stories="parser-lexical-scalars">
Floats should be implemented as IEEE 754 binary64 values.
</requirement>
<requirement name="float-structure" stories="parser-lexical-scalars">
A float consists of an integer part (which follows the same rules as decimal integer values) followed by a fractional part and/or an exponent part. If both a fractional part and exponent part are present, the fractional part must precede the exponent part.
</requirement>
<requirement name="float-fractional-part" stories="parser-lexical-scalars">
A fractional part is a decimal point followed by one or more digits. The decimal point, if used, must be surrounded by at least one digit on each side.
</requirement>
<requirement name="float-exponent-part" stories="parser-lexical-scalars">
An exponent part is an E (upper or lower case) followed by an integer part (which follows the same rules as decimal integer values but may include leading zeros).
</requirement>
<requirement name="float-underscores" stories="parser-lexical-scalars">
Similar to integers, you may use underscores to enhance readability. Each underscore must be surrounded by at least one digit.
</requirement>
<requirement name="float-signed-zero" stories="parser-lexical-scalars">
Float values `-0.0` and `+0.0` are valid and should map according to IEEE 754.
</requirement>
<requirement name="float-special-values" stories="parser-lexical-scalars">
Special float values can also be expressed. They are always lowercase.
</requirement>
<requirement name="boolean" stories="parser-lexical-scalars">
Booleans are just the tokens you're used to. Always lowercase.
</requirement>
<requirement name="offset-datetime" stories="parser-datetimes">
To unambiguously represent a specific instant in time, you may use an RFC 3339 formatted date-time with offset.
</requirement>
<requirement name="datetime-space-separator" stories="parser-datetimes">
For the sake of readability, you may replace the T delimiter between date and time with a space character (as permitted by RFC 3339 section 5.6).
</requirement>
<requirement name="datetime-fractional-precision" stories="parser-datetimes">
Millisecond precision is required. Further precision of fractional seconds is implementation-specific. If the value contains greater precision than the implementation can support, the additional precision must be truncated, not rounded.
</requirement>
<requirement name="local-datetime" stories="parser-datetimes">
If you omit the offset from an RFC 3339 formatted date-time, it will represent the given date-time without any relation to an offset or timezone.
</requirement>
<requirement name="local-date" stories="parser-datetimes">
If you include only the date portion of an RFC 3339 formatted date-time, it will represent that entire day without any relation to an offset or timezone.
</requirement>
<requirement name="local-time" stories="parser-datetimes">
If you include only the time portion of an RFC 3339 formatted date-time, it will represent that time of day without any relation to a specific day or any offset or timezone.
</requirement>
<requirement name="array-values" stories="parser-arrays-inline">
Arrays are square brackets with values inside. Whitespace is ignored. Elements are separated by commas. Arrays can contain values of the same data types as allowed in key/value pairs. Values of different types may be mixed.
</requirement>
<requirement name="array-multiline" stories="parser-arrays-inline">
Arrays can span multiple lines. A terminating comma (also called a trailing comma) is permitted after the last value of the array. Any number of newlines and comments may precede values, commas, and the closing bracket. Indentation between array values and commas is treated as whitespace and ignored.
</requirement>
<requirement name="inline-table-syntax" stories="parser-arrays-inline">
Inline tables are fully defined within curly braces: `{` and `}`. Within the braces, zero or more comma-separated key/value pairs may appear. Key/value pairs take the same form as key/value pairs in standard tables. All value types are allowed, including inline tables.
</requirement>
<requirement name="inline-table-single-line" stories="parser-arrays-inline">
Inline tables are intended to appear on a single line. A terminating comma (also called trailing comma) is not permitted after the last key/value pair in an inline table. No newlines are allowed between the curly braces unless they are valid within a value.
</requirement>
<requirement name="inline-table-closed" stories="parser-arrays-inline">
Inline tables are fully self-contained and define all keys and sub-tables within them. Keys and sub-tables cannot be added outside the braces.
</requirement>
<requirement name="inline-table-no-extension" stories="parser-arrays-inline">
Similarly, inline tables cannot be used to add keys or sub-tables to an already-defined table.
</requirement>
<requirement name="table-headers" stories="parser-tables">
Tables (also known as hash tables or dictionaries) are collections of key/value pairs. They are defined by headers, with square brackets on a line by themselves.
</requirement>
<requirement name="table-scope" stories="parser-tables">
Under that, and until the next header or EOF, are the key/values of that table.
</requirement>
<requirement name="table-no-order" stories="parser-tables">
Key/value pairs within tables are not guaranteed to be in any specific order.
</requirement>
<requirement name="table-naming" stories="parser-tables">
Naming rules for tables are the same as for keys
</requirement>
<requirement name="table-whitespace" stories="parser-tables">
Whitespace around the key is ignored.
</requirement>
<requirement name="implicit-super-tables" stories="parser-tables">
You don't need to specify all the super-tables if you don't want to. TOML knows how to do it for you.
</requirement>
<requirement name="empty-tables" stories="parser-tables">
Empty tables are allowed and simply have no key/value pairs within them.
</requirement>
<requirement name="table-defined-once" stories="parser-tables">
Like keys, you cannot define a table more than once. Doing so is invalid.
</requirement>
<requirement name="tables-out-of-order" stories="parser-tables">
Defining tables out-of-order is discouraged.
</requirement>
<requirement name="root-table" stories="parser-tables">
The top-level table, also called the root table, starts at the beginning of the document and ends just before the first table header (or EOF). Unlike other tables, it is nameless and cannot be relocated.
</requirement>
<requirement name="dotted-keys-define-tables" stories="parser-tables">
Dotted keys create and define a table for each key part before the last one, provided that such tables were not previously created.
</requirement>
<requirement name="table-header-and-dotted-key-conflicts" stories="parser-tables">
Since tables cannot be defined more than once, redefining such tables using a `[table]` header is not allowed. Likewise, using dotted keys to redefine tables already defined in `[table]` form is not allowed. The `[table]` form can, however, be used to define sub-tables within tables defined via dotted keys.
</requirement>
<requirement name="array-of-tables" stories="parser-tables">
These can be expressed by using a header with a name in double brackets. The first instance of that header defines the array and its first table element, and each subsequent instance creates and defines a new table element in that array. The tables are inserted into the array in the order encountered.
</requirement>
<requirement name="array-of-tables-reference" stories="parser-tables">
Any reference to an array of tables points to the most recently defined table element of the array.
</requirement>
<requirement name="array-parent-defined-first" stories="parser-tables">
If the parent of a table or array of tables is an array element, that element must already have been defined before the child can be defined. Attempts to reverse that ordering must produce an error at parse time.
</requirement>
<requirement name="static-array-no-append" stories="parser-tables">
Attempting to append to a statically defined array, even if that array is empty, must produce an error at parse time.
</requirement>
<requirement name="table-array-conflict" stories="parser-tables">
Attempting to define a normal table with the same name as an already established array must produce an error at parse time. Attempting to redefine a normal table as an array must likewise produce a parse-time error.
</requirement>
